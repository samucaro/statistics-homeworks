In Ethereum (and Bitcoin) a private key is an integer k and the public key is the point Q = k·G on the elliptic curve secp256k1, where G is a fixed base point. Computing Q from k is fast; recovering k from Q is the Elliptic Curve Discrete Logarithm Problem (ECDLP), believed to be infeasible for a 256-bit curve. This page reproduces the idea on a toy curve small enough to compute by hand, then asks which statistical properties of the outputs are meaningful for cryptography.

Educational code: arithmetic is not constant-time and the toy curves offer no security at all (the private key can be found by trying every value). Never use it with real keys.

1. Setup: curve, base point, private key required

Toy curve E: y² = x³ + 7 (mod 17) — same equation as secp256k1 (a = 0, b = 7) but over the field F17 instead of Fp with p ≈ 2256. It has , where O is the "point at infinity", the neutral element of the group (it plays the role of 0).

Point addition — the only operation we need

Points are added with the chord-and-tangent rule; over Fp every division is a multiplication by a modular inverse (computed with the extended Euclidean algorithm). For P = (x₁, y₁), Q = (x₂, y₂):

P + O = P                          (O is the neutral element)
P + (−P) = O,   where −(x, y) = (x, −y mod p)
λ = (y₂ − y₁) · (x₂ − x₁)⁻¹  mod p     if P ≠ Q   (chord)
λ = (3x₁² + a) · (2y₁)⁻¹    mod p     if P = Q   (tangent, "doubling")
x₃ = λ² − x₁ − x₂  mod p
y₃ = λ(x₁ − x₃) − y₁  mod p          →   P + Q = (x₃, y₃)

3. A faster method: double-and-add required

Write k in binary and scan it from the most significant bit: for each bit, double the accumulator R; if the bit is 1, also add G. This is the same idea as fast modular exponentiation (square-and-multiply), written additively. The cost is at most 2·log₂(k) operations — about 512 for a 256-bit key instead of ≈ 2256. That gap between O(log k) forward and the best known ≈ √n backwards (Pollard's rho) is what makes k ↦ kG a one-way function.

5.1 The assignment's curve (p = 17)

Orders of the 17 affine points. By Lagrange's theorem the order of every point divides the group order 18:

Frequency of x in kG, k = 1 … n−1
Frequency of y in kG, k = 1 … n−1

Observations (they hold for any G chosen in §1):

  • Periodicity. k·G depends only on k mod n (n = order of G). With G = (1, 5), n = 9: there are only 9 possible public keys, so the "private key" can be found by trying all of them.
  • Symmetry. (n − k)·G = −(k·G): the x-coordinate is repeated in pairs and the y values come as y / 17 − y.
  • No meaningful statistics. With 8 points, histograms, χ² tests or bit counts cannot distinguish "uniform" from "structured". This motivates §5.2.

The top bit (bit 11) is almost always 0 simply because x < p = 2089 < 212: only x ≥ 2048 set it. That is a property of the range, not a weakness of the map. For secp256k1, p = 2256 − 232 − 977 is so close to 2256 that the effect is negligible. The standard error uses N/2 because each x appears twice (±y).

(d) Correlation between input k and output x(kG)

Over the full range the correlation is exactly 0 — "too perfect": it is forced by the symmetry x(kG) = x((n−k)G), which makes x a symmetric function of k around n/2. On the half range (each x once) the values fall inside the band expected for unrelated data. Zero linear or monotonic correlation does not mean independence: the relation is exact and algebraic, just not visible to these statistics.

(e) Avalanche-like behaviour: flip one bit of k

Baseline: HD between x of two random points

If the two distributions match, a one-bit change of the key produces a public key that is, bit-wise, as different as an unrelated one. Note: k′G = kG ± 2ʲG, so the two outputs are still exactly related by the group law.

Conclusions

  1. Statistics can falsify, not certify. A strong bias would reveal a weakness, but passing every test proves nothing: the p = 2089 curve passes χ², bit balance, correlation and avalanche tests, yet its private keys are recovered by trying 2143 values. Security comes from the size of the group and the hardness of ECDLP, not from good-looking histograms.
  2. kG is not a hash, and should not be. Its value comes precisely from the group structure that a hash must destroy: with it, Alice and Bob agree on a shared secret (a·bG = b·aG), and signatures can be verified using only Q. A random oracle could not do that.
  3. Avalanche and uniformity are by-products here, not requirements. They emerge because scalar multiplication mixes the coordinates very thoroughly, but nobody designs secp256k1 for them; for SHA-256 / Keccak they are explicit design criteria.
  4. Careful with naive statistics. Exact zero correlation (forced by symmetry) and duplicated samples (±y) can make tests look better — or more significant — than they are. Effective sample size matters.
  5. Parameters matter beyond size. Example: y² = x³ + 7 mod 547 also has a prime number of points, but exactly p of them; such "anomalous" curves are broken in polynomial time by Smart's attack. Real curves are chosen to avoid known weak classes.

This is exactly where §6 becomes concrete: the one-way function (kG) protects the key, the hash turns the public key into a short identifier and adds a second layer: until an address spends, only its hash is public.

7.2 Statistics inside the protocols

  • Proof-of-Work as a probabilistic process (Bitcoin). Each hash attempt is a Bernoulli trial with success probability target / 2256, so the number of attempts is geometric and block arrivals are well modelled as a Poisson process, with exponential inter-block times (mean 10 minutes). Every 2016 blocks the difficulty is retargeted: the network estimates the hash rate from the observed time and rescales the target — a statistical estimator steering the system.
  • Double-spend probability. The Bitcoin whitepaper (§11) models an attacker catching up as a gambler's-ruin random walk, with the attacker's progress during the wait modelled by a Poisson distribution; this is the origin of the "wait for 6 confirmations" rule of thumb.
  • Randomness in Proof-of-Stake (Ethereum). Block proposers are drawn pseudo-randomly, with probability proportional to effective balance, from the RANDAO beacon (a mix of BLS signatures revealed by proposers). The last proposer can withhold its reveal and bias the result by about one bit — a known, accepted limitation, analysed in probabilistic terms.
  • Data availability sampling (Ethereum). Since EIP-4844 (2024), rollups post "blobs" committed with KZG polynomial commitments. With the Fusaka upgrade (December 2025), PeerDAS (EIP-7594) lets nodes download only random samples of erasure-coded blob data. Because the data is extended with redundancy, missing data would make many samples fail, so the probability of accepting unavailable data decreases exponentially with the number of samples: a direct application of sampling theory to security.
  • Passkeys on-chain. Fusaka also added a precompile for the NIST curve secp256r1 (EIP-7951), used by Secure Enclave, Android Keystore and FIDO2/WebAuthn, so wallets can be controlled by hardware-backed keys.

7.3 Statistics as an attack and as a defence

  • Bad randomness in ECDSA nonces. An ECDSA signature uses a fresh secret nonce. Reusing it twice reveals the private key with simple algebra (the 2010 PlayStation 3 break; Android wallets in 2013 because of a flawed random generator). Even a slight statistical bias is enough: Breitner and Heninger (2019) applied lattice attacks to biased nonces and recovered hundreds of Bitcoin keys and dozens of Ethereum keys. Modern wallets use deterministic nonces (RFC 6979). This is where "statistical properties desirable for cryptography" matter most: the randomness of secrets, more than the look of public outputs.
  • Key generation. A private key is only as strong as the entropy behind it; "brain wallets" (keys derived from human passphrases) have been emptied by attackers enumerating likely phrases.
  • Chain analytics. Blockchains are pseudonymous, not anonymous: heuristics such as common-input ownership, change detection and timing analysis cluster addresses statistically — used by investigators and compliance teams, and a privacy risk for users.
  • Looking ahead. Shor's algorithm would solve ECDLP in polynomial time on a large fault-tolerant quantum computer. Hashed addresses protect keys only until they are first used, which is why post-quantum migration is an open research topic for both chains.
