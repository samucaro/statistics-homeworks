2. Five different jobs required

The assignment asks to distinguish these clearly. The most useful test is: is it secret? is it reversible? does it need randomness?

ConceptWhat it doesRandom?Reversible?Security goalIn the pipeline
Key generationCreates a new secret from fresh randomnessYes—Unpredictability (entropy)Entropy for BIP-39
Key derivationComputes new keys deterministically from an existing secretNoNo (one-way)Children reveal nothing about parent/siblings; same input → same keysPBKDF2 (BIP-39), BIP-32/44

Typical confusions: a mnemonic is an encoding of the key material, not encryption; a hash is not encryption (there is no key and nothing to decrypt); a checksum stops typos, but an attacker can always compute a valid checksum for their own address.

4. Role and purpose of each standard required

BIP-39 — mnemonic and seed

Turns 128–256 bits of entropy into 12–24 words from a fixed list of 2048 (11 bits per word), adding a checksum of ENT/32 bits from SHA-256. Then stretches the words (plus an optional passphrase) into a 512-bit seed with PBKDF2-HMAC-SHA512 (2048 iterations). Purpose: a backup humans can write down and type back reliably.

BIP-32 — hierarchical deterministic keys

From the seed, HMAC-SHA512 produces a master private key and a chain code. Each child key is HMAC-SHA512(chain code, parent key data ‖ index), added to the parent key mod n. Purpose: one backup → unlimited keys, organised as a tree. Hardened children (index ≥ 2³¹) need the parent private key; normal children can be derived from the parent public key (watch-only wallets).

BIP-44 — standard paths

Fixes the meaning of the tree levels: m / purpose' / coin_type' / account' / change / address_index; Ethereum uses m/44'/60'/0'/0/i (60 = Ether in SLIP-44). Purpose: interoperability, so different wallets find the same accounts from the same phrase.

secp256k1 — public-key cryptography

The elliptic curve y² = x³ + 7 over a 256-bit prime field (see HW1). Q = k·G links private and public key; ECDSA signatures over this curve prove ownership of k without revealing it. Purpose: authorisation of transactions.

Keccak-256 — hashing

The address is the last 20 bytes of Keccak-256(x ‖ y). It is also used everywhere else in Ethereum (transaction hashes, storage slots, function selectors). Purpose: a short, fixed-size identifier that hides the public key until it is used.

EIP-55 — checksummed addresses

Encodes check bits in the case of the hex letters: letter i is uppercase iff the i-th hex digit of Keccak-256(lowercase address) is ≥ 8. Purpose: detect typos while staying backward compatible (lowercase addresses remain valid, just unchecked).

5. Statistical properties required

Each primitive has a different statistical target. Entropy must be uniform; derived keys and hashes must look independent of their inputs; checksums must catch errors with a known probability. All experiments run in your browser on demand. Tests and formulas are the ones described in HW1 §5.0 (χ² goodness-of-fit, bit frequencies with ±2 standard errors, Pearson/Spearman correlation, Hamming distance).

5A. BIP-39: are the words uniform? How good is the checksum?

All word positions
12th word only (7 random bits + 4 checksum bits)

Uniform entropy ⇒ every word equally likely (2048 = 2¹¹, so no word is favoured). Even the last word, which contains the checksum, is uniform overall. But given the first 11 words, only 128 of the 2048 candidates for the 12th are valid: the 4-bit checksum lets a random wrong word slip through with probability 1/16 = 6.25%. A checksum is error detection, not security.

Key stretching: what PBKDF2 buys

With 128 bits of entropy, brute force is hopeless even without PBKDF2. Stretching matters when the secret is weak: a short passphrase, or a phrase with missing words. Example: one unknown word → 2048 candidates, of which the checksum leaves 128 — recovered in well under a second. The security of the whole wallet is the entropy of the generation step; every later step is deterministic and adds none.

5B. Keccak-256: does the address look random?

Hex digits of addresses (dashed = expected)

Inputs are random 64-byte strings standing in for public keys (computing real ones costs ≈ 20 ms each). For a well-behaved hash the number of changed bits is Binomial(m, ½): mean m/2, standard deviation √m/2.

5C. BIP-32: do sibling keys look unrelated?

Consecutive indices i, i+1 differ by one bit, yet the child keys differ in about half of their 256 bits and show no correlation with the index: the HMAC behaves like a pseudo-random function. This is what makes sharing one child key (or address) harmless for its siblings — with one important exception: a normal child private key together with the parent extended public key (xpub) reveals the parent private key, because k_child − k_parent = I_L is computable from public data. Hardened derivation exists to block this.

5D. EIP-55: how many check bits does an address carry?

Observed number of letters
Model

Each of the 40 hex characters is a letter (a–f) with probability 6/16, so the number of letters L ~ Binomial(40, 6/16), mean 15. Only letters carry a case bit, so a random change passes with probability 2−L. Averaging over L: E[2−L] = (1 − 6/16 + 6/16 · ½)40 = (13/16)40 ≈ 0.0247%, the figure quoted in EIP-55 — but it depends on the address: one with few letters is much less protected. Compare: BIP-39 12 words → 4 check bits (1/16); Bitcoin Base58Check → 32 check bits.

6. Historical context required

YearMilestoneRole in the pipeline

2009Bitcoin launched addedsecp256k1 + SHA-256; the BIPs below are Bitcoin proposals

2013BIP-39 — mnemonic codeHuman-readable backup → seed
2014BIP-44 — multi-account hierarchyStandard paths, incl. coin type 60 for Ether

The pattern is that the wallet pipeline is assembled from older parts: general-purpose primitives (hash functions, elliptic curves) came first and are standardised by bodies like NIST/SECG; the wallet-specific standards (BIPs, EIPs) are community proposals from 2012 onwards that combine those primitives to solve usability problems — backups, many accounts, interoperability, typos.

7. SHA-2 / SHA-512 vs Keccak / SHA-3 required

SHA-2 (SHA-256, SHA-512)Keccak / SHA-3
DesignersNSA, published by NIST (2001)Bertoni, Daemen, Peeters, Van Assche — winner of an open NIST competition
ConstructionMerkle–Damgård: a compression function iterated over blocksSponge: absorb the input into a 1600-bit state, then squeeze the output
Internal state256 / 512 bits (equal to output)1600 bits; 512 hidden "capacity" bits for 256-bit output
Length-extension attackVulnerable: H(m) lets you compute H(m ‖ pad ‖ x) without m (why HMAC exists)Not vulnerable: the capacity is never output
StatusUnbroken, ubiquitousUnbroken; standardised as a backup with a different design, not because SHA-2 failed
In this pipelineSHA-256: BIP-39 checksum · SHA-512: HMAC in PBKDF2 and BIP-32Keccak-256: address and EIP-55

Keccak-256 vs SHA3-256. Same permutation, same rate (1088 bits) and capacity (512 bits). The only difference is the padding: before the pad10*1 rule, SHA-3 appends the domain-separation bits 01 (byte 0x06), while the original Keccak appends nothing extra (byte 0x01). NIST introduced this change while drafting FIPS 202; Ethereum had already adopted Keccak as submitted, so its "SHA3" is not the standard SHA3-256. For the empty string: Keccak-256 = c5d24601…5d85a470 (a constant often seen in Ethereum as the hash of empty code), SHA3-256 = a7ffc6f8…80f8434a.

8. Why several primitives instead of one? required

StageProblem it solvesProperty neededWhy another primitive cannot do it
BIP-39 / 32 / 44Backup and manage many keysDeterministic, human-friendly, hierarchical, interoperableA hash alone gives no tree, no chain codes, no xpub/watch-only and no word encoding
secp256k1Prove ownership publiclyAlgebraic structure: anyone verifies with Q, only k signsA hash has no structure → cannot verify a signature (HW1: kG is not a hash, and must not be)
Keccak-256Short identifierRandom-looking, collision-resistant, fixed sizeA curve point is 64 bytes and structured; hashing compresses to 20 bytes and hides Q until first use
EIP-55Humans copy addressesError detection, backward compatibleNo secret involved, so cryptographic strength is not the goal; it reuses Keccak only as a cheap source of check bits

It is the separation of concerns principle from security architecture: each component has one job and one threat model, can be analysed and replaced independently (e.g. a post-quantum signature scheme could replace secp256k1 without changing BIP-39), and a weakness in one layer does not automatically break the others — e.g. a typo-tolerant address format does not weaken the keys.

9. Checking it against real wallet software suggested

Wallets such as MetaMask, Rabby, Exodus or Rainbow implement the same pipeline behind a "Secret Recovery Phrase" screen. A safe way to observe each component:

  1. Use a separate browser profile, never your real wallet, and only the public test vector above (anyone can spend funds sent to it).
  2. Import the phrase: the first account should show 0x9858EfFD…aEda94, identical to §3 — the same BIP-39 seed and BIP-44 path m/44'/60'/0'/0/0.
  3. Add accounts: wallets increment the last index (…/0/1, …/0/2). Compare with the "Address index" field in §3.
  4. Change one word: most wallets refuse it immediately — that is the BIP-39 checksum of §5A at work.
  5. Copy an address and change one character in the "send" field: wallets flag invalid EIP-55 checksums (§5D).

Observation worth discussing: wallets do not all iterate the same level of the path (some vary the account level instead of the address index), so the same phrase can show different addresses in different wallets. The keys are not lost — they are on another branch of the BIP-32 tree. This is exactly why BIP-44 exists, and why it is only partially effective.
